# 运行记录与应用日志

每次运行不论来源都留下一条**运行记录**和一份**运行日志**：记录是结论（谁、何时、跑得怎么样、产出了什么），日志是过程（那一次的完整输出流）。术语见 [CONTEXT.md](../CONTEXT.md) 的「运行」「运行记录」「运行详情」「日志」。

两者都放在可执行文件同级，不入仓库（`.gitignore` 里有 `runs/` 与 `logs/`）：

```
<exe 目录>/
├── runs/
│   └── <run-id>/
│       ├── run.json        运行记录本体
│       └── events.ndjson   运行日志：输出事件逐行落盘
└── logs/
    └── app.log             应用日志：调度与运行器自身的行迹
```

## 哪些运行会留档

| 来源 | 留档 | `origin` |
|------|------|----------|
| 界面上手动运行动作 / 工作流 / AI 任务 | 是 | `manual` |
| 调度到点自动运行 | 是 | `schedule` |
| 调度卡上的「立即运行」 | 是 | `run-now` |

- **到点被跳过**（目标正在运行）也留一条，状态 `skipped`、原因写明撞上了谁——跳过不是失败，留档但不覆盖该目标上一次真实运行的结果。它没有运行过程，所以没有 `events.ndjson`
- **启动失败**（目标已被卸载、参数不合法这类早于占锁的失败）同样留一条 `failed`，没有过程
- **被拒绝的手动运行**不留档：目标正在运行时再点运行，后端直接返回「正在运行」，这次运行根本没有开始
- **工作流的步骤不单独留档**：动作步骤与 AI 步骤的输出带步骤归属，落在所属工作流那一次运行的日志里
- CLI（`workflow-tool run`）的运行暂不留档，随独立执行器一起接入

## run-id

`r<启动时刻>-<随机后缀>`，如 `r20261124-021500-a1b2c3`：启动时刻精确到秒（本地时间），后缀是 6 位十六进制。目录名即 id。同一秒内的多次启动靠随机后缀区分。

## run.json

键名用 snake_case：

```json
{
  "id": "r20261124-021500-a1b2c3",
  "target": { "kind": "ai", "id": "xdzs-verify-fix" },
  "origin": "schedule",
  "schedule_id": "nightly-verify",
  "params": { "CASE_INPUT": "{\"header\":{}}", "prompt": "只看崩溃线程" },
  "status": "succeeded",
  "reason": "",
  "started_at": "2026-11-24T02:15:00.482+08:00",
  "finished_at": "2026-11-24T02:19:12.107+08:00",
  "exit_code": 0,
  "outputs": { "text": "…", "session_id": "…", "cost_usd": "0.12" },
  "process": { "mode": "in-app", "pid": 4321, "started_at": "2026-11-24T02:00:00.012+08:00" },
  "rules": "# 无人值守守则\n…"
}
```

| 字段 | 含义 |
|------|------|
| `id` | run-id |
| `target` | 目标：`kind` 为 `action` / `workflow` / `ai`，`id` 是它的 id |
| `origin` | 发起来源，三选一：`schedule` / `run-now` / `manual` |
| `schedule_id` | 由调度发起时有：那条调度的 id |
| `params` | 本次运行的输入**原样**留存，含保留运行参数（`prompt` / `system` / `resume`）；模板展开不在这里，看到的就是当时传进来的 |
| `status` | 见下表 |
| `reason` | 失败原因、跳过原因、中断原因；成功与取消为空 |
| `started_at` / `finished_at` | 起止时刻。`finished_at` 缺省 = 尚未结束，或中断（结束时刻不可知，不编造） |
| `exit_code` | 退出码；没有有效退出码时省略（跳过、启动失败、中断） |
| `outputs` | 产出。动作：`##[output]` 自定义键 + `exit_code` / `success` / `stdout` / `stderr`；AI 任务：`text` / `thinking` / `session_id` / `cost_usd` / token 用量（见 [ai.md](ai.md)「产出」）。留档时已失败或还没产出则为空 |
| `process` | 承载本次运行的进程：`mode` 目前恒为 `in-app`；`pid` 是应用进程，`started_at` 是该进程的启动时刻。两者一起核对进程身份——只比 `pid` 不够，它会被复用。`started_at` 取的是进程内记下的第一个时刻（比真正的创建时刻晚一个运行时初始化的时长，但不同进程必然不同）。跳过与启动失败没有这个字段 |
| `rules` | 仅 AI 运行有：本次注入的无人值守守则全文。守则文件改版后，只有这里能还原当时注入的是什么 |

### 状态

| `status` | 含义 |
|----------|------|
| `running` | 进行中 |
| `succeeded` | 成功结束 |
| `failed` | 失败：命令非零退出、构造阶段出错，或**超时**。超时是失败不是取消，`reason` 注明超时 |
| `cancelled` | 人主动终止（点「停止」、取消所属工作流） |
| `interrupted` | 因应用退出或崩溃而没能得出结果 |
| `skipped` | 调度到点时目标正在运行，这次没有发起 |

### 终态只写一次

`run.json` 在启动时写一次（`running`），结束时写一次终态。任何路径都不再改写已终结的记录。

应用启动时会逐条检查遗留的 `running` 记录：应用内的运行随应用退出必然终止，所以它们一律改写为 `interrupted`（原因「应用退出时仍在运行，未能得出结果」），结束时刻留空，并在应用日志里记一条 `run.interrupted`。无法解析的 `run.json` 跳过不动，记一条 `run.record.unreadable`。

## events.ndjson（运行日志）

该次运行的输出事件逐行落盘，**与前端当时收到的事件同构**——运行详情用它回放，看到的就是当时界面上的样子。

每行一个 JSON 对象：

```json
{"t":120,"event":"output","stream":"ai","line":"你好","seq":1}
{"t":900,"event":"output","stream":"ai-tool","line":"{\"id\":\"t1\",\"name\":\"Read\",\"input\":{}}","seq":2}
{"t":3700,"event":"done","exitCode":0,"err":"","duration":"3.7s","seq":3,"readout":{"durationMs":3700,"sessionId":"…"}}
```

- `t`：相对启动时刻的毫秒偏移。前端实时归约工序段用的是到达时刻，回放用它，两者得到同样的时间轴
- `event`：`output`（一条输出）或 `done`（结束）
- `output` 行的其余字段就是事件 payload：`stream` / `line` / `seq`；工作流的输出多一个 `step`（步骤归属）。三种目标的 `seq` 都从 1 递增（`done` 行不取号），回放据此排序；运行中的记录被打开时，详情页「先订阅、后读盘」，读盘之前的事件会被重送一遍，也靠 `seq` 去重
- `done` 行：`exitCode` / `err` / `duration` / `seq` / `readout`
- 契约定义在 `internal/api/events.go`，落盘与推送给前端是同一处代码

**大小上限 16MB**。持续输出的动作（logcat-stream）与超大体积的树帧会让日志无限增长，到达上限后停止落盘并写一行 `{"event":"truncated","limit":16777216}`，运行详情据此提示「其后的输出没有落盘」。

## 保留策略

- 每个目标最多保留 **50 次**运行，超出时清理最老的
- 被跳过的到点**单独计**这 50 次：跳过不覆盖上一次真实运行的结果，也不能把真实记录挤出保留窗口（否则一条每分钟到点、目标长期被占用的调度，不到一小时就能让最近结果落空）
- 超过 **30 天**的记录一律清理
- 正在运行的不清理
- 清理在新记录写入时与应用启动时执行；只清理能识别的记录，`runs/` 下的其他东西不碰

## 应用日志

`logs/app.log`，NDJSON，单文件 5MB，保留 3 份（当前文件加两份轮转备份）。记录调度与运行器自身的行迹：

```json
{"time":"2026-11-25T02:15:00.103+08:00","event":"schedule.trigger","origin":"schedule","run_id":"r20261125-021500-a1b2c3","schedule_id":"nightly-verify","target_kind":"ai","target_id":"xdzs-verify-fix"}
```

| `event` | 何时 |
|---------|------|
| `schedule.trigger` | 调度到点并发起了一次运行 |
| `schedule.skipped` | 到点撞上运行中的目标，留档为跳过 |
| `schedule.launch_failed` | 到点后启动失败 |
| `run.interrupted` | 启动时把遗留的运行中记录改写为中断 |
| `run.record.unreadable` | `runs/` 下有一份无法解析的记录，已跳过 |
| `run.start.failed` / `run.note.failed` / `run.finish.failed` | 运行记录本身写不进去（日志只影响留档，不影响运行） |
| `run.prune.failed` | 清理旧记录失败 |

日志写不进去永远不影响运行。错过（`missed`）与认领（`claim`）的行迹随独立执行器接入时加入。

## 界面

**入口**：侧栏「配置」分组的「运行记录」；调度卡最近结果旁的状态、AI 卡的调度投影、会话页的运行记录抽屉都直达某一次运行的详情。

**运行记录列表**：全部目标，按时间倒序；可按目标种类与目标、状态、来源筛选。每行是目标、状态、开始时刻、耗时与发起来源；AI 运行的摘要显示当次提示词（按当次输入展开变量）。

**运行详情**是全应用唯一查看运行过程的地方：

- **结论**：状态、原因、起止时刻、耗时、退出码、发起来源与调度
- **过程**：从运行日志回放。动作是输出行（stderr 着色、进度行原地覆盖、树帧照常渲染）；AI 任务是工序段面板（思考 / 工具调用 / 回答，带段级耗时与终点读数）；工作流是步骤 spine，AI 步骤同样是工序段
- **产出**与**输入**：读数类产出（会话 id、费用、token、自定义 output）与本次输入；正文类产出（回复、stdout）只在过程里呈现一次
- AI 运行另有可展开的「本次注入的无人值守守则」

**运行中的记录**在回放之上订阅该目标的实时事件，继续应用；跑完后自动换成完整回放。调度发起的运行前端没有它的输出捕获，所以 AI 卡在那种运行进行中点卡身，去的就是运行详情。

**会话页右上角的「运行记录」**是这个任务的运行记录抽屉：列出它的历次运行，点一条即把它的会话 id 回填到「续接会话」并进入运行详情。旧版本把会话记录存在浏览器 localStorage 的 `ai-history:<id>` 里，现在不再读取。

## 对前端的事件

| 事件 | payload |
|------|---------|
| `runs:changed` | `{run_id, status, target_kind?, target_id?}` |

一条运行记录被创建或写终态时发出。前端只把它当作「有变化」的信号：重新拉取列表与详情，并刷新 AI 任务列表（卡片摘要取自最近一次运行）。

## 尚未实现

以下属于后续里程碑（独立执行器），现在没有：

- 调度运行不随应用退出（执行器、心跳认领、停止标记）
- 错过的调度时刻（`missed`）与补跑开关（`catch_up`）
- 运行详情里的「续跑」
