# 运行记录与应用日志

每次运行不论来源都留下一条**运行记录**和一份**运行日志**：记录是结论（谁、何时、跑得怎么样、产出了什么），日志是过程（那一次的完整输出流）。术语见 [CONTEXT.md](../CONTEXT.md) 的「运行」「运行记录」「运行详情」「日志」。

两者都放在可执行文件同级，不入仓库（`.gitignore` 里有 `runs/` 与 `logs/`）：

```
<exe 目录>/
├── runs/
│   ├── <run-id>/
│   │   ├── run.json        运行记录本体
│   │   ├── events.ndjson   运行日志：输出事件逐行落盘
│   │   ├── STOP            停止标记：应用写入、执行器见到即取消（仅执行器运行期间存在）
│   │   └── executor.log    执行器进程自己的标准输出与标准错误（正常情况下是空的）
│   └── locks/              目标锁，每个目标一个文件（见「目标锁」）
├── logs/
│   └── app.log             应用日志：调度与运行器自身的行迹
└── schedules.state.json    调度器上次评估到的时刻（见「错过与补跑」）
```

## 哪些运行会留档

| 来源 | 留档 | `origin` | 谁来跑 |
|------|------|----------|--------|
| 界面上手动运行动作 / 工作流 / AI 任务 | 是 | `manual` | 应用进程内 |
| 调度到点自动运行 | 是 | `schedule` | 独立执行器 |
| 调度卡上的「立即运行」 | 是 | `run-now` | 独立执行器 |
| 调度开启了 `catch_up`，应用恢复后补跑 | 是 | `schedule` | 独立执行器 |

- **到点被跳过**（目标正在运行）也留一条，状态 `skipped`、原因写明撞上了谁——跳过不是失败，留档但不覆盖该目标上一次真实运行的结果。它没有运行过程，所以没有 `events.ndjson`
- **到点被错过**（应用没在运行）留一条 `missed`，同样没有过程（见「错过与补跑」）
- **启动失败**（目标已被卸载、执行器没能拉起这类早于运行的失败）同样留一条 `failed`，没有过程
- **被拒绝的手动运行**不留档：目标正在运行时再点运行（含运行详情里的「续跑」），后端直接返回「正在运行」，这次运行根本没有开始
- **工作流的步骤不单独留档**：动作步骤与 AI 步骤的输出带步骤归属，落在所属工作流那一次运行的日志里
- 直接从 shell 发起的 `workflow-tool run` 不留档：它是给 Agent 的一次性调用，输出直接回到终端

## run-id

`r<启动时刻>-<随机后缀>`，如 `r20261124-021500-a1b2c3`：启动时刻精确到秒（本地时间），后缀是 6 位十六进制。目录名即 id。同一秒内的多次启动靠随机后缀区分。

## run.json

键名用 snake_case：

```json
{
  "id": "r20261124-021500-a1b2c3",
  "target": { "kind": "ai", "id": "xdzs-verify-fix" },
  "origin": "schedule",
  "schedule_id": "nightly-verify",
  "params": { "CASE_INPUT": "{\"header\":{}}", "prompt": "只看崩溃线程" },
  "status": "succeeded",
  "reason": "",
  "started_at": "2026-11-24T02:15:00.482+08:00",
  "finished_at": "2026-11-24T02:19:12.107+08:00",
  "exit_code": 0,
  "outputs": { "text": "…", "session_id": "…", "cost_usd": "0.12" },
  "process": { "mode": "executor", "pid": 4321, "started_at": "2026-11-24T02:15:00.512+08:00", "heartbeat_at": "2026-11-24T02:19:11.900+08:00" },
  "rules": "# 无人值守守则\n…"
}
```

| 字段 | 含义 |
|------|------|
| `id` | run-id |
| `target` | 目标：`kind` 为 `action` / `workflow` / `ai`，`id` 是它的 id |
| `origin` | 发起来源，三选一：`schedule` / `run-now` / `manual` |
| `schedule_id` | 由调度发起时有：那条调度的 id |
| `params` | 本次运行的输入**原样**留存，含保留运行参数（`prompt` / `system` / `resume`）；模板展开不在这里，看到的就是当时传进来的 |
| `status` | 见下表 |
| `reason` | 失败原因、跳过原因、错过原因、中断原因；成功与取消为空 |
| `started_at` / `finished_at` | 起止时刻。`finished_at` 缺省 = 尚未结束，或中断（结束时刻不可知，不编造） |
| `exit_code` | 退出码；没有有效退出码时省略（跳过、错过、启动失败、中断） |
| `outputs` | 产出。动作：`##[output]` 自定义键 + `exit_code` / `success` / `stdout` / `stderr`；AI 任务：`text` / `thinking` / `session_id` / `cost_usd` / token 用量（见 [ai.md](ai.md)「产出」）。留档时已失败或还没产出则为空 |
| `process` | 承载本次运行的进程。`mode` 为 `in-app`（应用进程内）或 `executor`（独立执行器）；`pid` 与 `started_at` 是该进程的 pid 与启动时刻，两者一起核对进程身份——只比 `pid` 不够，它会被复用。`started_at` 取的是进程内记下的第一个时刻（比真正的创建时刻晚一个运行时初始化的时长，但不同进程必然不同）。执行器运行另有 `heartbeat_at`，运行期间每 10 秒回写一次。跳过与错过没有这个字段；执行器没能拉起的启动失败带着它，但没有 `pid` |
| `rules` | 仅 AI 运行有：本次注入的无人值守守则全文。守则文件改版后，只有这里能还原当时注入的是什么 |

### 状态

| `status` | 含义 |
|----------|------|
| `running` | 进行中 |
| `succeeded` | 成功结束 |
| `failed` | 失败：命令非零退出、构造阶段出错，或**超时**。超时是失败不是取消，`reason` 注明超时 |
| `cancelled` | 人主动终止（点「停止」、取消所属工作流） |
| `interrupted` | 因应用或执行器退出、崩溃而没能得出结果 |
| `skipped` | 调度到点时目标正在运行，这次没有发起 |
| `missed` | 调度到点时应用没在运行，这个时刻溜走了 |

`skipped` 与 `missed` 都只是到点的留痕，不是一次运行：它们不覆盖上一次真实运行的结果，调度卡的「最近结果」也不取它们。

### 终态只写一次

`run.json` 在启动时写一次（`running`），结束时写一次终态。任何路径都不再改写已终结的记录。

运行期间唯一会回写 `run.json` 的是执行器的心跳（只动 `process.heartbeat_at`）。终态由**跑这次运行的一方**写：应用内的运行由应用写，执行器的运行由执行器写。应用只在一种情况下替执行器写终态——核对后确认执行器已经不在了，此时写的是 `interrupted`。

## 进程模型

按发起来源分两条路径：

- **手动运行**留在应用进程内。应用退出时终止，留档为 `interrupted`。
- **调度到点与立即运行**交给**执行器**：应用建好运行记录后，拉起同一可执行文件的 `run --record <run-id> --allow-ai` 子命令。它是独立进程，不随应用退出而终止，自己把运行日志、心跳与终态落进那条记录。执行器进程带环境标记 `WORKFLOW_TOOL_EXECUTOR=1`；它是 headless 的 `run` 子命令，本来就不组装应用、不启动调度器，定时任务不会再拉起定时任务。它**先接手记录**（写下自己的 pid 与首次心跳）**再加载目标与依赖**：接手前记录里没有 pid 也没有心跳，先加载再接手的话，应用侧的核对循环会在这段空窗里把运行误判成中断（见下「认领」的接手宽限）

应用仍在须在到点时运行。本设计不接管系统级定时。

### 认领

应用启动时逐条检查遗留的 `running` 记录：

- `process.mode` 是 `in-app`：应用内的运行随应用退出必然终止，一律改写为 `interrupted`（原因「应用退出时仍在运行，未能得出结果」），结束时刻留空，并在应用日志里记一条 `run.interrupted`
- `process.mode` 是 `executor`：**心跳新鲜**（10 秒一跳，30 秒内算新鲜）就认领——继续显示为运行中，运行详情可跟踪日志，也能停它；**心跳过期**时核对 `pid` 与 `started_at`（防 pid 复用），进程仍在就再等，不改写；确认不在的改写为 `interrupted`（原因「执行器退出时仍在运行，未能得出结果」），记一条 `run.interrupted`
- `process.pid` 还是 0（执行器被拉起后**尚未接手**）：没有心跳与进程身份可核对，启动对账与每 2 秒的核对都给 **30 秒接手宽限**（`AttachGrace`，按记录的 `started_at` 起算）——宽限内一律视为仍在运行，过了宽限仍没接手才改写为 `interrupted`。执行器先接手再加载，这段盲窗正常只有进程启动本身；宽限盖住的是慢启动与拉起后即刻退场的残留。误判「还没接手」为「执行器没了」会让执行器随后的接手必然失败（`attach run ...: already interrupted`），那次运行就真的什么都没跑

认领在应用打开运行记录之后立刻进行：仍在运行的执行器运行会登记进进程内的簿记，调度卡显示为运行中。应用开着的时候每 2 秒核对一次在途的执行器运行：执行器自己写了终态，就同步索引、更新调度卡、发 `runs:changed`（只清属于那条记录的进程内登记——执行器结束后同一目标上可能刚开始了新的运行，不能按目标误清）；执行器没了（心跳过期且进程不在），同样留中断。被执行器落在 skipped 的到点同样只更新「上次到点」的留痕，不覆盖上一次真实运行的结果。

无法解析的 `run.json` 跳过不动，记一条 `run.record.unreadable`。

### 停止

- 应用内的运行：取消它的 ctx，运行器杀掉整个进程组
- 执行器的运行：应用在该次运行的目录下写 `STOP` 文件，执行器每秒轮询，见到即取消——同样经 ctx 传导、杀进程组，以 `cancelled` 收尾；终态落定后标记一并清掉。不依赖 POSIX 信号，Windows 同样可用

运行详情页的「停止」对两种运行都可用：它按目标寻址，后端按这次运行由谁承载决定走哪条路。

杀进程组之后，运行器会等管道关闭；没在 0.5 秒内关闭就再补杀一次进程组。这是因为组长恰好在 fork 途中被杀时，刚出世的孩子会躲过第一次组杀、继续握着管道（不补杀的话取消会一直卡到它自然结束）。

## 目标锁

同一个目标同一时刻只有一个运行，跨进程成立：应用内的手动运行、独立执行器、Agent 从 shell 发起的 `workflow-tool run` 都经同一把**落盘的目标锁**互斥，工作流的动作步骤与 AI 步骤也各占自己目标的锁。

每个目标一个文件 `runs/locks/<kind>-<id>.lock`，内容是持有者的 `pid` 与启动时刻；持有者结束即释放。持有者崩溃时文件会留下，下一次占锁按进程身份核对：持有者已不在就是残留，接管。

## 错过与补跑

调度器把每条调度**上次被评估到的时刻**持久化在 `schedules.state.json`（每个 tick 过后就是当前这一分钟）。应用恢复后，从那一刻到现在之间的每个到点都是**错过**：

- 每个错过的时刻留一条 `missed` 运行记录，原因写明是哪一刻（「应用未在运行，错过 2026-11-24 02:15 的到点」），应用日志记 `schedule.missed`
- 一条调度一次恢复最多留 50 条错过：每分钟一条的调度停用一个月就是四万多个时刻，只保留最近的
- 调度写了 `catch_up: true` 时，报完错过后为**最近一个错过的时刻**补发一次运行（`origin` 仍是 `schedule`），应用日志记 `schedule.catch_up`。补跑与恢复后第一个到点的常规运行撞上同一个目标时，后者照常跳过

不算错过的几种情况：

- 调度**停用**期间的到点：停用时刻照常推进，重新启用后不翻旧账
- 调度**改了时间规则**（`cron`）：旧时刻不再可用，不按新规则去翻旧账
- 没有「上次评估时刻」的调度（刚建、或上次运行早于本功能）：不编造错过
- 时钟回拨：回拨本身不是错过，也不会把记录改早（否则时间回到原处会把处理过的时刻再报一遍）

应用开着但系统睡眠时 tick 会断档，断档里的到点同样被当作错过报出。

## events.ndjson（运行日志）

该次运行的输出事件逐行落盘，**与前端当时收到的事件同构**——运行详情用它回放，看到的就是当时界面上的样子。应用内的运行与执行器的运行写出的日志是同一个形状。

每行一个 JSON 对象：

```json
{"t":120,"event":"output","stream":"ai","line":"你好","seq":1}
{"t":900,"event":"output","stream":"ai-tool","line":"{\"id\":\"t1\",\"name\":\"Read\",\"input\":{}}","seq":2}
{"t":3700,"event":"done","exitCode":0,"err":"","duration":"3.7s","seq":3,"readout":{"durationMs":3700,"sessionId":"…"}}
```

- `t`：相对启动时刻的毫秒偏移。前端实时归约工序段用的是到达时刻，回放用它，两者得到同样的时间轴
- `event`：`output`（一条输出）或 `done`（结束）
- `output` 行的其余字段就是事件 payload：`stream` / `line` / `seq`；工作流的输出多一个 `step`（步骤归属）。三种目标的 `seq` 都从 1 递增（`done` 行不取号），回放据此排序；运行中的记录被打开时，详情页「先订阅、后读盘」，读盘之前的事件会被重送一遍，也靠 `seq` 去重
- `done` 行：`exitCode` / `err` / `duration` / `seq` / `readout`
- 契约定义在 `internal/runstore` 的 `LogEmitter`，落盘与推送给前端是同一个 payload

**大小上限 16MB**。持续输出的动作（logcat-stream）与超大体积的树帧会让日志无限增长，到达上限后停止落盘并写一行 `{"event":"truncated","limit":16777216}`，运行详情据此提示「其后的输出没有落盘」。

## 保留策略

- 每个目标最多保留 **50 次**运行，超出时清理最老的
- 没有发起运行的到点（跳过、错过）**单独计**这 50 次：它们不覆盖上一次真实运行的结果，也不能把真实记录挤出保留窗口（否则一条每分钟到点、目标长期被占用的调度，不到一小时就能让最近结果落空）
- 超过 **30 天**的记录一律清理
- 正在运行的不清理
- 清理在新记录写入时与应用启动时执行；只清理能识别的记录，`runs/` 下的其他东西不碰

## 应用日志

`logs/app.log`，NDJSON，单文件 5MB，保留 3 份（当前文件加两份轮转备份）。记录调度与运行器自身的行迹（只有应用进程写；执行器不写它）：

```json
{"time":"2026-11-25T02:15:00.103+08:00","event":"schedule.trigger","origin":"schedule","run_id":"r20261125-021500-a1b2c3","schedule_id":"nightly-verify","target_kind":"ai","target_id":"xdzs-verify-fix"}
```

| `event` | 何时 |
|---------|------|
| `schedule.trigger` | 调度到点并发起了一次运行 |
| `schedule.skipped` | 到点撞上运行中的目标，留档为跳过 |
| `schedule.missed` | 应用恢复后，为一个错过的调度时刻留档 |
| `schedule.catch_up` | 为最近一个错过的时刻补发运行 |
| `schedule.launch_failed` | 到点后启动失败 |
| `schedule.executor_failed` | 执行器没能拉起（记录与调度卡已交代，这里只记行迹） |
| `run.claimed` | 启动时认领了一条仍在运行的执行器运行 |
| `run.interrupted` | 启动时或核对中把一条运行中记录改写为中断 |
| `run.record.unreadable` | `runs/` 下有一份无法解析的记录，已跳过 |
| `run.stop.failed` | 停止标记写不进去 |
| `run.start.failed` / `run.note.failed` / `run.finish.failed` / `run.heartbeat.failed` / `run.poll.failed` | 运行记录本身写不进去或读不出来（日志只影响留档，不影响运行） |
| `run.prune.failed` | 清理旧记录失败 |

日志写不进去永远不影响运行。

## 界面

**入口**：侧栏「配置」分组的「运行记录」；调度卡最近结果旁的状态、AI 卡的调度投影、会话页的运行记录抽屉都直达某一次运行的详情。

**运行记录列表**：全部目标，按时间倒序；可按目标种类与目标、状态、来源筛选。每行是目标、状态、开始时刻、耗时与发起来源；AI 运行的摘要显示当次提示词（按当次输入展开变量）。

**运行详情**是全应用唯一查看运行过程的地方：

- **结论**：状态、原因、起止时刻、耗时、退出码、发起来源与调度
- **过程**：从运行日志回放。动作是输出行（stderr 着色、进度行原地覆盖、树帧照常渲染）；AI 任务是工序段面板（思考 / 工具调用 / 回答，带段级耗时与终点读数）；工作流是步骤 spine，AI 步骤同样是工序段
- **产出**与**输入**：读数类产出（会话 id、费用、token、自定义 output）与本次输入；正文类产出（回复、stdout）只在过程里呈现一次
- AI 运行另有可展开的「本次注入的无人值守守则」
- **停止**：运行中的记录右上角有「停止」，应用内的运行与执行器的运行都能停
- **续跑**：AI 运行结束后，只要留下了会话 id，就有「续跑」——以同一份输入加 `resume: <session_id>` 发起一次新的手动运行，并进入新运行的详情

**运行中的记录**在回放之上继续跟踪：应用内的运行订阅该目标的实时事件；执行器的运行没有实时事件可订阅（它在另一个进程里），每 2 秒重读一次运行日志。跑完后都自动换成完整回放。调度发起的运行前端没有它的输出捕获，所以 AI 卡在那种运行进行中点卡身，去的就是运行详情。

**会话页右上角的「运行记录」**是这个任务的运行记录抽屉：列出它的历次运行，点一条即把它的会话 id 回填到「续接会话」并进入运行详情。旧版本把会话记录存在浏览器 localStorage 的 `ai-history:<id>` 里，现在不再读取。

## 对前端的事件

| 事件 | payload |
|------|---------|
| `runs:changed` | `{run_id, status, target_kind?, target_id?}` |
