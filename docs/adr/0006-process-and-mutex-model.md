# 调度运行交给独立执行器，手动运行留在应用内；互斥按目标、冲突只跳过

应用一旦退出，它拉起的子进程会在下一次写 stdout 时随之死掉（实测，管道持有者没了），工作流执行器更是应用内的一个 goroutine——所以今天的定时任务在应用退出后必然夭折，「记录进程信息、重启后同步进度」也无从谈起。现约定按发起来源分两条进程路径：调度到点与立即运行交给独立执行器（同一可执行文件的 headless `run` 子命令，标准输出重定向到运行日志文件），不随应用退出，应用重启后按运行记录里落盘的进程信息认领（pid、启动时间与执行器心跳）；手动运行留在应用进程内，应用退出时终止并记为中断。互斥统一按目标：同一目标同一时刻只有一个运行，不论来自手动、调度还是工作流步骤；工作流的动作步骤与 AI 步骤同样占目标锁，撞上立即失败而不是等待。调度到点撞上则记为跳过而不是失败，不排队。

## Considered Options

- 全量走执行器：只有一条运行路径，最简单；但聊天里的手动运行要跨进程流式渲染、随时追问，交互成本高。
- 一律中断、不做续跑：零新进程模型；但定时任务随应用退出夭折，「退出再进同步进度」无法满足。
- 按发起来源分流：无人值守的运行可续、交互式的运行保持现状；代价是两条运行路径共用同一份运行记录与锁，锁必须是跨进程的。

## Consequences

- 目标锁从应用内存态变为落盘的跨进程锁；应用内的「正在运行」判断全部改读它。
- 执行器启动时带环境标记，调度器在执行器进程内不启动，避免定时任务再拉起定时任务。
- 手动运行在应用退出时被终止并留档为中断；执行器运行的可以被人主动停止，记为取消。
- 现有工作流行为变化：步骤撞上正在运行的同名目标时以前照跑，现在失败。
- 应用仍须在到点时运行；本决策不接管系统级定时（launchd）。
