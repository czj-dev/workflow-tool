# AI 任务脱离动作体系，成为第三种可执行物

LLM 曾是动作的第四种执行形态（`command.llm`），但两者的前提相反：动作是「给定输入得到确定结果」，AI 委托是「给定目标、由 Agent 自行决定路径」。共存于同一 schema 只能靠特判维持——动作默认 60s 超时对 AI 不适用、CLI 入口要单独拦截 LLM、表单得先分辨哪个参数是 prompt、哪个是 system。现把 AI 任务独立定义（一任务一文件），`command.llm` 连同全部相关逻辑删除，不留兼容入口也不留提示，既有 LLM 动作静态改写为 AI 任务。同时保留「工作流以一步调用一个 AI 任务」：AI 任务的价值在于彼此组合，组合的载体仍是工作流。

## Considered Options

- 软剥离：AI 任务独立，但 `command.llm` 作为兼容入口保留过渡期。旧文件零改动，代价是同一能力两处定义，特判在过渡期内一处不少。
- 硬剥离并去掉工作流调用：边界最干净，但 AI 任务只能单发，无法编排。
- 硬剥离并保留工作流 AI 步骤：单一事实来源，组合能力不丢；代价是没有过渡期。

## Consequences

- 动作 YAML 解析不拒绝未知键：残留 `command.llm` 的文件不会得到专门提示，只会因缺少执行形态而落入通用的必填校验报错。
- 动作 schema 回到确定性执行这一种语义；AI 任务 schema 按自身需要独立演进。
- 工作流步骤多一种类型（AI 步骤），调度多一种目标（见 ADR-0005）。
- 「LLM Action」「LLM 卡」统一改称「AI 任务」「AI 卡」，ADR-0001 中的旧称按此理解。
