# 无人值守的 AI 运行放开到 bypass 权限，环境守则由运行器注入

AI 任务要能定时运行，有两件事不能指望每个任务作者自己处理好。其一是权限：headless 进程里没有任何确认弹窗可点，一次确认请求就等于任务卡死到超时，所以所有 AI 运行都以 bypass 权限启动、不新增审批机制——这与 CLI 至今以「无人值守下放开权限」为由拒绝运行 LLM 动作的守卫相反，该守卫在执行器接入时改为显式放行。其二是行为约束：无人可问须自行决断、脚本用绝对路径、禁止后台子代理等异步续跑机制——这些描述的是运行器提供的环境而不是任务的角色，此前由三个任务各抄一份且已经漂移，现改为运行器在每次运行前统一注入，任务的 `system` 只写角色与纪律。

## Considered Options

- 运行中挂起、等人批准后继续：权限最小；但应用不在场时无人可批，与定时运行的前提矛盾。
- 沿用 CLI 的拒绝态度：最安全；但 AI 任务几乎都要读写文件和执行脚本，等于没有可定时运行的任务。
- 放开到 bypass，环境约束收归运行器：任务不会卡在确认上，守则只有一处；代价是定时任务拥有与当前用户相同的权限，`schedules.yaml` 的任何改动都等同于可执行代码的改动。

## Consequences

- M1 固定 bypass；任务级 `permission` 字段只在 schema 中约定、不实现，只读分析类任务与可写任务暂不区分。
- 守则全文随每次运行记录落档；任务的 YAML 不是发给 Agent 的完整系统提示。
- 调整守则只改一处；新增任务即使没抄守则也自带约束。
